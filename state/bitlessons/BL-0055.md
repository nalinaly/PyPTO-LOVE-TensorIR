# BL-0055: Canonical evidence order must come from the producer contract

## Failure

The real SM120 child serialized `supported_compute_dtypes` as
`["FP32", "BF16"]`, but the CPU finalizer expected the handwritten order
`["BF16", "FP32"]`. Both lists name the same semantic set, yet the finalizer
correctly failed closed because its exact-order assertion disagreed with the
producer's canonical representation.

## Lesson

`NvidiaTargetInfo` sorts data types by their stable numeric code. FP32 is
`0x34`, BF16 is `0x40`, so its canonical serialized order is FP32 then BF16.
The runner preserved that order; the finalizer fixture had hidden the wrong
assumption.

Evidence validators must share the producer's canonical contract. They must
not silently sort or convert evidence to a set during validation, because that
would erase ordering drift and weaken replay identity. Keep one ordered
contract tuple, require exact equality, and test reversed, missing, duplicate,
extra, unknown and wrong-type representations. Independently replay the
serialized TargetInfo so the same field is joined through both runtime and
compiler evidence.
