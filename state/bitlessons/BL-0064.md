# BL-0064: Matmul output dtype and normalized modes define the kernel

## Risk

PyPTO BF16-by-BF16 `tensor.matmul` naturally returns BF16, but pinned TensorIR
can lower BF16 operands only when the matmul result and MMA accumulator are
FP32. Emitting a direct BF16 TensorIR matmul is therefore not a harmless type
choice: it is outside the reviewed lowering contract and loses the required
FP32 accumulation semantics.

Transpose and launch geometry have similar semantic weight. TensorIR matmul
has no transpose flags, so changing signature strides to imitate
`a_trans`/`b_trans` would make the ABI describe a logical view instead of the
physical dense tensor. Layout normalization also removes unit output modes.
For decode `M=1`, the schedule is N-only; forcing an `[M,N]` tile vector has the
wrong cardinality even though the original HIR result is rank 2.

## Lesson

For the first structured matmul family, keep the public ABI BF16 but emit
BF16-by-BF16-to-FP32 TensorIR matmul followed by a nearest-even FP32-to-BF16
conversion. Represent transpose as an explicit rank-aware TensorIR transpose
view while retaining the original physical argument shape and dense stride
metadata.

Derive schedule arity from normalized non-unit output modes in order
`[B,M,N]`, inserting a synthetic extent one only when all modes disappear. K
uses the separate contraction tile and never contributes a grid dimension.
Flatten the product of output tile counts into grid X, and require matmul's
grid-shape descriptor to be `Result0` at ABI index 2.

Start with static dense BF16 rank-2 and equal-batch rank-3 inputs. Reject
dynamic shapes, mixed ranks, batch broadcasting, `c_matrix_nz`, accumulator
forms and direct BF16 TensorIR matmul. Source legality is not SM120 evidence:
unit-M decode, transposed BF16 inputs, Cubin assembly, numerical parity and
small-M/large-M performance each need separate gates.
