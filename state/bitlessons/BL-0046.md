# BL-0046: A strict artifact must bind bytes, ABI and build provenance together

Hashing a compiler options object and separately hashing a launch ABI does not
prove they describe the same kernel. Cross-check every schedule-derived fact
that reappears at launch: tile sizes, uniform signatures, flat argument widths,
entry names and loader requirements.

An ELF header plus an executable section is also not a usable Cubin proof. For
the pinned producer, validate the complete chain that the loader consumes:

- one CUDA entry symbol and its canonical text section;
- KPARAM ordinal/width/range records;
- PARAM_CBANK symbol, base and extent;
- constant-bank size and section;
- non-empty PT_LOAD permissions and coherent file-to-VA mapping.

Finally, exact revision strings are trustworthy only when dirty sources cannot
mint strict artifacts under clean commit names. Enforce provenance at configure
time and again as an always-run build dependency; watch Git ref changes so a
reused build directory cannot retain a stale self revision.

Keep the validator runtime-free. Real pinned-producer Cubins are the positive
acceptance cases; synthetic ELF images are boundary tests, not evidence that
the CUDA driver would execute arbitrary instruction bytes.
