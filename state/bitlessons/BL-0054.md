# BL-0054: CUDA parameter enumeration order is not signature order

## Failure

The first parameter-ABI repair correctly made dynamic dimensions and strides
four-byte `int32` values and removed the assumption that Driver-reported
parameter offsets are increasing. It still compared each live Driver parameter
width with the Artifact parameter at the same enumeration index. A CUDA Driver
may enumerate `CU_FUNC_PARAM_INFO` records in an order that differs from the
kernel signature, so a valid mixed-width dynamic kernel could still fail
prewarm.

## Lesson

Use each source for the property it actually owns:

- Cubin `KPARAM` ordinals define kernel-signature order and therefore the
  Artifact argument order.
- Driver parameter enumeration proves the live frame's offset ranges and width
  multiset, independent of enumeration order.
- The launch pointer array remains in Cubin/Artifact signature order; Driver
  offsets must never reorder it.

Mixed-width tests must be non-palindromic and include an exact reversed Driver
sequence. Symmetric widths or index-aligned fixtures can accidentally validate
an ordering assumption that the API does not guarantee. The final repair keeps
bounded overlap/frame checks, compares live and expected width multisets, and
verifies pointer arguments delivered to launch remain signature ordered.
