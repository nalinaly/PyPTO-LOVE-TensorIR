2. Ownership and dependency direction
-------------------------------------

  PyTorch / SGLang
          |
          v
  pypto-framework-plugins
          |
          v
  pypto-kernels
          |
          v
  pypto compiler/runtime
          |
          +--> internal TensorIR --> internal CUDA Tile / LLVM / CUDA driver

Rules:
  - No reverse imports.
  - PyPTO owns compiler-generic IR, target traits, codegen and runtime. It does
    not import Torch, SGLang or named operator-family implementations.
  - pypto-kernels owns every handwritten/high-performance algorithm, reference,
    schedule, benchmark and tuning record. It consumes only public PyPTO APIs.
  - pypto-kernels never imports torch, sglang, triton or flashinfer.
  - pypto-framework-plugins alone owns framework tensors, FX/Inductor nodes,
    SGLang metadata, custom-op registration and exact-source guards. It owns no
    algorithm or tuning choice.
  - A usable Triton must remain installed because pinned
    Scheduler.create_backend calls has_triton() for GPU devices. The exact
    Torch/Triton pair identity and workspace wheel are still open. Strict
    coverage means zero Triton model-forward kernels, not absence of the
    compatibility package.

Known gaps
  - CudaTileCompileOptions does not propagate the real 82-SM count into
    PipelineOptions, so SM120 can fall back to 148 SM.
    TileCandidateGenerator.cpp::getSmemCapacityBytes also uses 227 KiB for
    every cc>=100 while this target's opt-in CTA maximum is 101376 bytes.
    Thread both accepted TargetTraits resources through compiler/cache identity
    before trusting automatic candidate legality/performance; an explicit
    schedule may use maxCandidates=0 for the first smoke only.
  - CudaTileCompiler reads ambient TENSOR_IR strategy/candidate/debug/load
    overrides that are absent from CompileOptions::toUniqueString(). Strict
    compilation must reject or explicitly disable them, never mutate process
    environment around concurrent compilation.
  - CudaTileFrontendResult has complete entry/argument/grid metadata, but no
    versioned serialization. CudaTileRuntimeKernel hides the strategy objects;
    initialize is not actually synchronized and support/workspace are TODO.
  - A requested CudaTileArtifactKind::Cubin may return TileIR when no compatible
    assembler exists. Strict provenance inspects actual bytes/magic.
  - tileiras comes from CUDA 13.3.73 PATH. Record its exact executable; never
    install a second TensorIR CLI to hide its absence.

Packaging gate
  No nv_tensor_ir package, TensorIR/CUDA Tile public tool, or separate LLVM,
  MLIR, TensorIR or CUDA Tile runtime DSO may enter the wheel. Try parent-side
  EXCLUDE_FROM_ALL first; patch dependency install guards only if the staged
  install audit proves leakage.
